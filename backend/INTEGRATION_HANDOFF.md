## Установка и запуск для README участника 3

Команды выполняются из корня репозитория. Backend слушает только loopback,
один процесс/один ML-обработчик. Не запускайте два сервера с одним DATA_DIR.
Рабочая ветка участника 2: `codex/backend-integration`.

Windows PowerShell (проверено с Python 3.14.7):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-tested.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m backend
```

Linux/GPU и macOS (рекомендуемый участнику 1 Python 3.12; здесь не проверялся):

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m backend
```

`requirements-tested.txt` фиксирует проверенное окружение, включая тестовые
зависимости; `requirements.txt` — базовые диапазоны, `requirements-dev.txt` —
добавления для тестов/приёмочного клиента. `pip check` ошибок не обнаружил.
Основные проверенные версии: FastAPI 0.141.1, Starlette 1.7.0, uvicorn 0.53.0,
python-docx 1.2.0, Pydantic 2.13.5, pytest 9.1.1, httpx 0.28.1, tzdata 2026.4.
Starlette сообщает deprecation warning для своего TestClient с httpx; тесты проходят.
Тяжёлые зависимости и совместимость Python для ML проверяет участник 1 отдельно.

`.env` в корне загружается автоматически; существующее окружение имеет приоритет.
`DATA_DIR` по умолчанию `./data`; относительный путь считается от корня проекта,
а не от текущего рабочего каталога. В папке хранятся SQLite и `uploads/`.
`--data-dir` переопределяет настройку. Для резервной копии остановите сервер
и скопируйте всю папку данных, включая исходные записи.

Основная топология GPU: backend и Ollama на одной машине, UI обслуживает тот же
backend после сборки frontend. С локального компьютера:

```bash
ssh -L 8000:127.0.0.1:8000 USER@GPU_HOST
```

Открыть `http://127.0.0.1:8000`. Авторизация не реализована; публичный bind
не входит в стандартный запуск. Для разработки UI используется Vite с proxy /api.
Для раздачи UI из FastAPI сначала выполнить `npm install` и `npm run build`
в каталоге frontend (версионирование frontend lock-файла согласует участник 3).

## Стык участника 1

- Вызываются существующие `ml.process_audio(path, context, callback)` и
  `ml.process_text(text, context, callback)`; внешних hosted API и скрытых fallback нет.
- Контекст ровно `{title, occurred_at, timezone, participants}`.
- Callback принимает `transcribing`, `diarizing`, `extracting`; ошибка хранит стадию
  и сообщение модели. Исключение или неверный результат → `failed`, не demo.
- Пустой `speaker_id` допустим: backend не придумывает говорящего.
- При приёме результата ID задач один раз преобразуются UUIDv5 в пространстве
  встречи. Поэтому одинаковый текст в двух встречах не создаёт коллизии в реестре.
  При последующих редактированиях API возвращает/хранит те же ID.
- Нужны непустые segments/summary, существующие источники каждой ML-задачи;
  текстовый импорт обязан иметь нулевые аудиометки.
- Очередь хранится в SQLite через записи со статусом `queued`. Они возобновляются
  после перезапуска. Прерванные активные стадии получают `failed` с причиной;
  для повтора исходник нужно загрузить заново. Штатное завершение ждёт активную
  модель, ещё не начатые задания остаются в очереди.

## Стык участника 3 — обязательные исправления UI

1. **Результат ML сейчас теряется в редакторе.** `App.tsx`: `createMeeting`
   создаёт пустой draft queued-встречи, а polling меняет draft лишь при отсутствии
   ключа (`current[updated.id] ? current : ...`). При `review_ready` старый пустой
   draft остаётся. Нужно инициализировать draft реальным результатом при переходе
   из обработки в `review_ready`; пользовательских правок на стадии обработки нет.
   Проверка: загрузить запись, дождаться готовности без перезагрузки страницы;
   summary и actions должны появиться сразу, без ложных «несохранённых изменений».
2. **Хранить revision самого черновика.** Сейчас save отправляет новую
   `selected.revision` с потенциально старым draft. Сохранять нужно revision,
   на основе которого пользователь начал правку. При обновлении сервера обновлять
   только нетронутые черновики; при 409 предложить перезагрузить/сверить данные.
3. После отметки исполнения перечитать встречу: revision увеличивается,
   approved остаётся true. `refresh()` должен обновлять нетронутые drafts,
   иначе редактор показывает устаревшее состояние исполнения.
4. Для правки уже утверждённого протокола нужен явный режим редактирования.
   API PATCH сбрасывает approval; перед новым DOCX необходимо повторное утверждение.
5. Показывать `selected.timezone`, фактические providers и расположение обработки.
   `health.status == ok` означает доступность API, а не готовность моделей;
   на GPU данные обрабатываются на выделенном сервере.

Все endpoints и payload описаны в contracts/README.md; новые поля UI не нужны.
FastAPI-ошибки валидации нормализованы в `{detail: string}`. PATCH сохраняет
переданные ID; ID чужой встречи отклоняется с 409, дубли внутри списка — с 422.

Утверждение атомарно сохраняет отдельный снимок протокола в SQLite.
`export.docx` всегда использует этот снимок. Смена статуса выполнения увеличивает
revision, но не меняет содержимое утверждённого DOCX. Повтор одинаковой отметки
статуса и повтор утверждения актуальной версии идемпотентны.

Уведомления формируются только для approved/open с конкретной due_date;
overdue — до сегодняшней даты встречи, due_soon — сегодня и до +3 дней включительно.
ID = action_id:due_date:kind, повторный GET не создаёт записи/дубли.
Относительный/событийный срок с due_date=null не создаёт уведомления.

## Настоящая приёмка после подготовки GPU

Этот клиент ходит в HTTP API, проверяет провайдеры и не подменяет inference.
Нужны backend/requirements-dev.txt и настоящий аудиофайл. `.venv/bin/python`
в Windows заменяется на `.\.venv\Scripts\python.exe`.

```bash
.venv/bin/python scripts/check_models.py --strict
.venv/bin/python -m backend.smoke upload --audio /path/to/meeting.wav --title "Рабочая встреча" --occurred-at 2026-09-23 --output artifacts/real-review.json
```

Дата должна совпадать с датой записи. JSON содержит ID, revision, сегменты,
результат модели и вопросы проверки. Сверить с записью/источниками, исправить
summary/participants/actions и очистить только разрешённые review_reasons.
Не менять ID, статус, revision и исходные segments. После ручной проверки:

```bash
.venv/bin/python -m backend.smoke review --input artifacts/real-review.json --approve --docx artifacts/real-protocol.docx
```

Без `--approve` сохраняются только исправления. Устаревшая revision даёт 409;
нельзя обходить конфликт автоматической подстановкой текущей версии.
Клиент проверяет открытие DOCX и число задач; качество ASR/диаризации/извлечения
и вёрстку документа оценивает человек. После этого отдельно проверить в UI
реестр, отметку исполнения, локальные напоминания и сохранение после перезапуска.

До реального прогона на GPU и исправлений UI полную готовность объявлять нельзя.
