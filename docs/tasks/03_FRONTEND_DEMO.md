# Участник 3 — интерфейс, проверка сценария и защита

Твоя цель: сделать понятный веб-интерфейс, через который секретарь проходит весь сценарий, и подготовить воспроизводимую демонстрацию. Участник 1 отвечает за модели/GPU, участник 2 — за backend и интеграцию. Ты также владелец README и сценария защиты.

## Общая картина

«Хаттама» превращает запись встречи в проверяемый протокол. Встречи могут быть на русском, казахском или смешанном языке. На выходе — реплики с говорящими, summary, поручения с исполнителем/сроком/источниками, DOCX и реестр исполнения. Секретарь подтверждает результат перед использованием.

```text
Создать встречу → загрузить запись → увидеть этап обработки
  → проверить summary и поручения → перейти к исходной реплике
  → исправить исполнителя/срок → сохранить → утвердить
  → скачать DOCX → контролировать выполнение
```

Главная ценность интерфейса — быстро понять, откуда взялось поручение и что ещё требует проверки. Пользователь не должен разбираться в библиотеках, GPU или JSON для прохождения основного сценария.

Времени — 4 часа. Оценка: работоспособность 25, техника 25, README/воспроизводимость 25, ценность 15, потенциал 10. README и демонстрация — значимая часть результата, а не работа «если останется время».

## Принятые решения

- React + TypeScript + Vite, обычный CSS, локальные ресурсы. Backend — FastAPI, данные — SQLite и файлы.
- Пользователь работает на M2/8 GB RAM; модели планируются на GPU Brev. По его сообщению организаторы разрешили обработку тестовых записей на самостоятельно развёрнутых моделях.
- Готовые внешние inference API не входят в пайплайн. Ключи OpenAI/NVIDIA не нужны в браузере.
- Основной вход — файл записи из любой платформы. Это не означает автоматическое подключение бота к Zoom/Meet/Teams; на лендинге/защите формулировать точно.
- DOCX обязателен в выбранном объёме; PDF, захват вкладки и Telegram — дополнительные этапы.
- Приложение содержит отдельный подготовленный вымышленный demo-пример для знакомства с интерфейсом. Его наличие не доказывает качество моделей.

## Экран 1: встречи и создание

- Список встреч: название, дата, источник, этап обработки/ошибка, утверждено или черновик.
- Основное действие — «Новая встреча».
- В форме: название, дата встречи, часовой пояс (по умолчанию Asia/Almaty), участники, аудио/видеофайл.
- Ограничение 100 MB; список поддерживаемых форматов брать из контракта. Ошибки показывать рядом с действием.
- Отдельный текстовый импорт: честно указать, что он проверяет извлечение поручений без распознавания голоса.
- Отдельная кнопка «Открыть демо»: видимая пометка «Вымышленные данные · готовый пример» сохраняется на всех следующих экранах.
- Для записей пользователь подтверждает, что участники уведомлены об обработке; не обещать автоматически уведомлять участников внешних платформ.

## Экран 2: обработка

Показывать реальные стадии `queued`, `transcribing`, `diarizing`, `extracting`, `review_ready`, `failed`. Достаточно опроса backend раз в несколько секунд. Процент готовности показывать только при реальном источнике прогресса, иначе — этап.

Проверка моделей вынесена в компактный статус/настройку. Отсутствие модели не маскируется бесконечным спиннером или demo-ответом. Ошибка должна объяснять, что сделать дальше, сохраняя доступ к списку встреч.

## Экран 3: проверка протокола

- Заголовок встречи, дата, источник, версия и статус утверждения.
- Краткое summary.
- Транскрипт: говорящий, текст, время только для настоящего аудио. Для текстового/demo-входа не рисовать фиктивные таймкоды.
- Участников можно сопоставить с голосовыми кластерами; не называть это распознаванием личности по тембру.
- Карточки/таблица поручений: действие, исполнитель, исходная формулировка срока, календарная дата если известна, причины проверки.
- «Источник» переводит к конкретной реплике; при наличии аудио — возможность прослушать соответствующий момент.
- Исполнитель и дата редактируются. Отсутствующий срок остаётся «Не указан»/событийной формулировкой.
- Причина проверки снимается явным подтверждением пользователя после проверки, а не автоматически при открытии карточки.
- Сначала «Сохранить», затем «Утвердить». Несохранённые правки нельзя потерять из-за polling или утвердить незаметно.
- Конфликт версии 409 показывает сообщение и предлагает обновить данные; локальный черновик не затирается молча.
- Экспорт DOCX доступен для сохранённой утверждённой версии. После правки содержания утверждение снимается.

Внешний вид: спокойный рабочий интерфейс, контрастный текст, светлая поверхность, один акцентный цвет, чёткие состояния. Поддержать узкое окно и клавиатуру. Состояния нельзя различать только цветом.

## Экран 4: поручения и напоминания

Фильтры «Все», «В работе», «Просрочено», «Выполнено». У каждой задачи — встреча, исполнитель, срок и действие завершения. Сервер рассчитывает просрочку, UI отображает результат.

Список локальных напоминаний доступен без Telegram. Если Telegram ещё не реализован/разрешён, не показывать «подключён» и не имитировать отправку. Можно обозначить его как план развития на защите.

## Контракт с backend

Прочитай [contracts/README.md](../../contracts/README.md) перед кодом. Все запросы идут на `/api`, Vite перенаправляет их на backend `127.0.0.1:8000`. В production готовую сборку может отдавать backend.

Нужные маршруты: `health`, список/получение `meetings`, создание через `meetings/audio`, `meetings/text`, `meetings/demo`, PATCH встречи, `approve`, `export.docx`, `audio`, `actions`, `notifications`.

Редактирование и утверждение передают актуальную `revision`. После успешного ответа сохранять серверную версию. Пустые nullable-поля не превращать в фиктивные значения. Все источники отображаются по `evidence_segment_ids`; времена — миллисекунды.

Пока ML готовится, используй серверный demo-route. Фронтенд не должен подменять сетевую ошибку собственными «успешными» данными.

## План на четыре часа

| Время | Работа | Проверяемый результат |
| --- | --- | --- |
| 0–15 | Прочитать контракт, проверить заготовки, каркас экранов и README | Сборка стартует, схема понятна |
| 15–45 | Список, создание, прогресс, demo-route | Можно открыть вымышленный пример через backend |
| 45–75 | Транскрипт, источники, редактор | Реальные данные отображаются, правки сохраняются |
| 75–120 | Утверждение и DOCX | Пользователь проходит весь путь с реальным результатом |
| 120–165 | Реестр, ошибки, языковые кейсы вместе с участником 1 | Статусы работают, RU/KZ символы отображаются |
| 165–210 | Проверить запуск по README, QA, подготовить защиту | Другой участник повторяет сценарий по инструкции |
| 210–240 | Репетиция, резервное видео, только исправления | Трёхминутная демонстрация без неожиданных действий |

Если к 120-й минуте нет полного пути, отложить PDF, анимации, захват вкладки, Telegram-экраны и второстепенные настройки. После 165-й минуты новые функции не добавлять.

## Проверка сценария

- [ ] Вымышленное demo заметно отличается от настоящего аудио.
- [ ] Создание встречи, ожидание, ошибка и повторное открытие работают.
- [ ] Источник каждой задачи ведёт к правильной реплике.
- [ ] Исполнитель/дата/текст задачи сохраняются; обновление страницы показывает серверный результат.
- [ ] Polling не затирает несохранённую правку.
- [ ] Конфликт версий объяснён пользователю.
- [ ] Утверждение и экспорт соблюдают статус сохранения/проверки.
- [ ] DOCX скачивается и открывается; казахские буквы не теряются.
- [ ] Выполненная задача правильно отображается в реестре и не считается просроченной.
- [ ] Кнопки работают с клавиатуры, формы подписаны, узкое окно читаемо.
- [ ] При недоступном backend/моделях показана ошибка, а не ложный успешный результат.

Команды установки/сборки сверять с текущим `frontend/package.json`. После появления lock-файла использовать `npm ci`, для проверки — `npm run build`. Backend запускается по проверенной инструкции участника 2. Не объявлять проверку завершённой только потому, что TypeScript собрался: пройти сценарий в браузере.

## Защита на 3 минуты

- 0:00–0:20 — проблема: ручное протоколирование и потерянные поручения.
- 0:20–0:45 — загрузка короткой вымышленной смешанной записи, запуск обработки.
- 0:45–1:30 — результат: говорящие, поручения, переход к реплике и исправление спорного поля.
- 1:30–2:10 — утверждение, DOCX, реестр и завершение задачи.
- 2:10–2:40 — реальная конфигурация моделей, результаты проверки RU/KZ/RU-KZ, воспроизводимый запуск.
- 2:40–3:00 — дальнейшее развитие: платформенные подключения, СЭД, разрешённые каналы уведомлений.

Если обработка длится дольше защиты, показать запуск и отдельно сохранённый результат, прямо назвав его заранее обработанным. Подготовить резервное видео полного прохода. На скриншотах/видео не должны оказаться ключи, купоны, платёжные данные или приватные встречи.
