# Участник 1 — модели, GPU и качество распознавания

Твоя цель: реальная запись на русском, казахском или смешанном языке должна превращаться в транскрипт с говорящими и проект протокола с поручениями. Ты отвечаешь за модели и доказательство качества; участник 2 — за backend и сборку; участник 3 — за интерфейс и защиту.

## Общая картина

Мы создаём «Хаттама» — помощника секретаря. Пользователь загружает запись, вводит дату встречи и участников. Приложение распознаёт речь, различает голоса, выделяет поручения и готовит саммари. Секретарь сверяет поручения с исходными репликами, исправляет имена/сроки, утверждает протокол и скачивает DOCX. Реестр показывает открытые, выполненные и просроченные задачи.

Пайплайн:

```text
Веб-интерфейс → FastAPI → файл + SQLite → фоновое задание
  → ASR → диаризация/сопоставление реплик → локальная LLM
  → структурированный проект → проверка секретарём
  → утверждение → DOCX + реестр + локальные напоминания
```

Времени — 4 часа, людей — 3. ТЗ даёт по 25 баллов за работоспособность, техническую реализацию и README/воспроизводимость; 15 — за пользу; 10 — за развитие. Дообучение не является обязательным. Главный результат — воспроизводимый полный сценарий.

## Принятые решения и ресурсы

- Mac M2 пользователя имеет 8 GB RAM. Основные модели размещаем на GPU в Brev; Mac — рабочее место разработчика.
- Подтверждён баланс Brev Compute $50. По сообщению пользователя организаторы разрешили обрабатывать тестовые записи на самостоятельно развёрнутых моделях в Brev.
- Это разрешение не означает разрешения отправлять записи в OpenAI API или готовые NVIDIA inference endpoints. Все этапы обработки встречи выполняются нашими моделями на выбранной машине.
- OpenAI-кредиты для основного сценария не требуются. Отдельно можно рассмотреть генерацию вымышленных примеров после готовности основы.
- На старт — одна GPU с 24–48 GB VRAM. Предпочтение доступной 48 GB машине с понятным тарифом; конкретный тип выбирается по фактической доступности Brev. Стоимость Runpod не переносим на Brev.
- Покупка/создание платной машины выполняется после согласования конкретной конфигурации и лимита расходов с владельцем аккаунта. API-ключи, купоны и приватные SSH-ключи остаются вне репозитория и переписки.
- Автоподключение к Zoom/Teams/Meet, обучение, live-транскрибация и распознавание личности по голосовому отпечатку — последующие этапы. MVP принимает запись.

## Что уже подготовлено

В репозитории есть общий план, [контракт](../../contracts/README.md), [вымышленный пример](../../fixtures/demo.json) и [смешанный текст](../../fixtures/mixed_meeting.txt). Начата разработка `backend/app/ml.py`; перед работой проверь фактическое содержимое и `git status`. Заготовка не означает, что реальные модели уже установлены или прошли проверку. На момент передачи доступ к GPU и полный inference не проверены.

На машине автора создана `.venv` с Python 3.12 для лёгких зависимостей приложения. На другой машине окружение нужно создать заново; `.venv` в Git не переносится.

Проверено при передаче: `ml.py` компилируется, 6 модульных тестов проходят. Диагностика не подтвердила доступность ASR, Ollama и диаризации на текущем Mac. Эти тесты проверяют валидацию/сопоставление, а не качество реальных моделей.

```bash
PYTHONPATH=backend .venv/bin/python -m unittest backend.tests.test_ml -v
.venv/bin/python scripts/check_models.py
```

Для GPU-профиля установи `backend/requirements-ml.txt` в окружение сервера, подготовь веса отдельно и выбери `ASR_DEVICE=cuda`. `DIARIZATION_MODEL_PATH` указывает на локальную папку модели; Ollama по умолчанию слушает `http://127.0.0.1:11434`, модель задаётся `OLLAMA_MODEL=qwen3:8b`. Конкретные CUDA/torch-версии проверь на выбранной машине до фиксации зависимостей.

## Твоя зона файлов

- `backend/app/ml.py` — реальный ML-пайплайн.
- `backend/requirements-ml.txt` — тяжёлые зависимости отдельно от веб-приложения.
- `backend/tests/test_ml.py` — проверка преобразований и валидации.
- `scripts/check_models.py` — диагностика доступности без скачивания весов.
- По необходимости `scripts/prepare_models.py`, `eval/`, `docs/ML_SETUP.md` — подготовка и измерение качества; заранее сообщи участнику 2 о новых файлах.

Участник 2 владеет общим HTTP-контрактом и backend вне ML, участник 3 — `frontend/`. Изменения форматов согласуются с участником 2 до изменения кода.

## Контракт с backend

Канонический источник — [contracts/README.md](../../contracts/README.md). Его нужно прочитать целиком перед кодом. Основной Interface:

```python
probe() -> dict
process_audio(path: str, context: dict, on_stage) -> dict
process_text(text: str, context: dict, on_stage) -> dict
```

`context` содержит встречу: название, дату `occurred_at`, `timezone`, участников. `on_stage` сообщает `transcribing`, `diarizing`, `extracting`. Возвращается словарь с `segments`, `summary`, `actions`, `warnings`. Хранение и HTTP-ответы делает участник 2.

Реплика: `id`, `start_ms`, `end_ms`, `speaker_id`, `text`.

Поручение: `id`, `title`, `assignee`, `due_text`, `due_date`, `evidence_segment_ids`, `review_reasons`, `status`.

- Неизвестный исполнитель — пустая строка и причина проверки.
- Неизвестная/событийная дата — `null`; исходная формулировка сохраняется в `due_text`.
- `evidence_segment_ids` ссылаются на реально существующие реплики.
- Для текстового импорта временные метки равны нулю; это не результат распознавания аудио.
- Отсутствующие веса, runtime или диаризация вызывают понятную ошибку. Система не заменяет их подготовленным саммари.

## Порядок выполнения

### 0–15 минут: подготовить вычисления

1. Проверить выбранную GPU, VRAM, доступ через SSH, свободный диск и Python/CUDA.
2. Уточнить фактический часовой тариф, лимит расходов и условия остановки. Для четырёхчасовой работы не нужно заранее оплачивать сутки.
3. Начать скачивание весов и зависимостей. Доступ к `pyannote/speaker-diarization-community-1` требует Hugging Face и принятия условий владельцем аккаунта — проверить сразу.
4. Передать участнику 2 способ запуска обработчика и локальный адрес Ollama. Приложение и модели предпочтительно работают на одной машине; доступ с Mac — через SSH-туннель.

Готово, когда есть проверенный доступ к GPU и понятный статус загрузки всех весов. Если нет, сразу сообщить команде — это риск критического пути.

### 15–45 минут: реально распознать короткий фрагмент

1. ASR-кандидат: мультиязычный Whisper large-v3 через faster-whisper. Начать с короткой записи, согласовать режим вычислений с VRAM.
2. Диаризация: локальный pyannote community-1, интервалы говорящих.
3. Конвертация записи в mono PCM 16 kHz через FFmpeg; метки времени привязаны к исходной записи.
4. Сопоставить реплики и голоса по временным интервалам. Неуверенные перекрытия отметить.
5. Имена участников предложить по списку/контексту, оставляя ручное подтверждение. Разделение голосов само по себе не сообщает имя человека.

Готово, когда 30–60 секунд реального аудио дают текст и реальные интервалы минимум двух голосов. Зафиксировать время и конфигурацию. Если не готово к 45-й минуте — остановить дополнительные функции и сообщить участнику 2.

### 45–75 минут: получить структурированный проект

1. Локальный Ollama + Qwen3-8B в подходящей квантизации. При недостатке памяти модели выполнять последовательно.
2. Передавать транскрипт с ID реплик, дату встречи, часовой пояс и участников.
3. Запрашивать структурированный JSON; проверить типы, ссылки, даты, уникальность и размер результата.
4. Поручение отделять от предложения и обсуждения. Говорящий и исполнитель могут быть разными людьми.
5. Повторы объединять. Если срок менялся, сохранять финальное согласованное значение; неоднозначность показывать секретарю.

Готово, когда `process_text` возвращает валидный результат по общему контракту, а backend показывает его в интерфейсе. Эталонное summary не включать во вход модели.

### 75–120 минут: полный путь

Прогнать первую предоставленную запись, вернуть данные участнику 2, вместе довести до DOCX. Ошибки исправлять по этапу: неверное слово — ASR; неверный голос — диаризация; неверная задача — извлечение. Если до 120-й минуты нет полного пути, команда откладывает Telegram/PDF/захват вкладки.

### 120–165 минут: три языковых сценария

Второй предоставленный пример плюс отдельные RU, KZ и RU/KZ записи. Для казахского и смешанного сценариев нужны короткие вымышленные диалоги минимум с двумя голосами, именами, числами и сроками. Не фиксировать `language=ru` на всю смешанную запись. Не включать режим перевода вместо транскрибации.

Готово, когда для каждого сценария сохранены вход, ожидаемые обязательства, фактический результат и ошибки. Участник 3 помогает подготовить записи и проверить казахский текст человеком.

### 165–240 минут: воспроизводимость и защита

Зафиксировать версии, веса/квантизацию, команды запуска, VRAM и время полного прохода. Проверить работу без внешнего inference после скачивания моделей. Передать участнику 3 короткое объяснение архитектуры и честные ограничения. После 210-й минуты — только исправления.

## Какие ошибки особенно проверять

- В первом примере 10 строк поручений; финальный повтор не порождает дубликаты.
- Исполнитель может быть отделом, а не человеком.
- «Две недели → три недели → 15 октября» требует корректного учёта уточнения.
- Во втором примере поручение получает не выступавший Ерлан.
- «После совещания» остаётся событием, а отсутствующий срок — отсутствующим.
- Смета за неделю и закрытие очереди за месяц — разные обязательства.
- Пустой/испорченный файл и отсутствие runtime дают ошибку, а не успешное фиктивное распознавание.

Сравнивать извлечение из эталонного текста и полный путь из аудио отдельно. В отчёте указать найденные/пропущенные/лишние поручения, правильность исполнителя и срока, проверенные интервалы говорящих. Результат на одной записи не объявлять общей точностью модели.
