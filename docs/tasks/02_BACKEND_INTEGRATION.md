# Участник 2 — backend, данные и сборка MVP

Твоя цель: собрать надёжный полный путь от загрузки записи до утверждённого DOCX и реестра поручений. Ты — владелец общего контракта и интегратор. Участник 1 отвечает за модели/GPU, участник 3 — за интерфейс, проверку сценария и защиту.

## Общая картина

«Хаттама» — помощник секретаря. Запись встречи на русском, казахском или смешанном языке превращается в транскрипт с говорящими, краткое саммари и задачи. Каждая задача содержит исполнителя, срок и ссылки на исходные реплики. Секретарь проверяет результат, исправляет неоднозначности и утверждает документ. Затем доступны DOCX, статусы исполнения и напоминания.

```text
React/Vite → FastAPI → SQLite + локальные файлы
                       ↓ очередь, один обработчик
                 ASR → диаризация → LLM
                       ↓
           черновик → проверка → утверждённая версия
                       ↓
                 DOCX / реестр / напоминания
```

Времени 4 часа, в команде 3 человека. Оценка: работоспособность 25, техническая реализация 25, README/воспроизводимость 25, польза 15, потенциал 10. Поэтому интеграция в первый час и проверяемый запуск — твоя главная задача.

## Ограничения и актуальные решения

- ТЗ запрещает отправку записей/текста в готовые внешние облачные inference API.
- У пользователя M2/8 GB RAM. По его сообщению организаторы разрешили тестовую обработку на самостоятельно развёрнутых моделях в Brev; подтверждены Brev Compute $50.
- Основные модели и при необходимости весь backend работают на GPU-машине. Mac подходит для лёгкого приложения, тестов и интерфейса. Согласуй топологию с участником 1; для демо проще один сервер и SSH-туннель.
- Импорт записи — основной вход. Автоматическое участие в Zoom/Teams/Meet, realtime, обучение моделей и интеграция СЭД не входят в обязательный объём.
- Экспорт сначала DOCX; PDF — дополнительная функция.
- Telegram — дополнительный отключаемый канал, не входит в офлайн-режим. Разрешение Brev не означает разрешения Telegram. До разрешения/готовности основной путь использует локальные уведомления.
- Сервер без авторизации держать на loopback и открывать через SSH-туннель. Публичный доступ требует отдельной настройки защиты.

## Твоя зона файлов и координация

- `backend/app/` кроме `ml.py` — HTTP, хранение, задания, экспорт, напоминания.
- `backend/requirements.txt`, backend-тесты кроме `test_ml.py`.
- `contracts/README.md` — изменения только после уведомления обоих участников.
- Корневые настройки запуска, `.env.example`, `.gitignore`, при необходимости контейнеризация.
- Технические команды запуска и переменные для README передаёшь участнику 3; README редактирует он, чтобы избежать конфликта.
- `fixtures/` — изменения согласовать с участником 1 и 3, не превращать эталон в подгонку под реализацию.

Каждый участник работает в отдельной ветке/клоне или worktree. Слияния небольшими готовыми частями. Общие схемы, lock-файлы и корневую конфигурацию меняет один владелец. Не ждать конца четырёх часов для первой интеграции.

## Общий контракт

Перед кодом прочитай [contracts/README.md](../../contracts/README.md) целиком. Он имеет приоритет над эскизом в старом плане. Все маршруты с `/api`.

Основные данные:

- Meeting: ID, название, дата встречи, часовой пояс, режим `audio|text|demo`, стадия обработки, версия, признак утверждения, участники, реплики, саммари, поручения, ошибки/предупреждения.
- Segment: ID, начало/конец в миллисекундах, speaker_id, текст.
- Action: ID, суть, исполнитель, исходный срок, подтверждённая дата либо null, ссылки на реплики, причины проверки, `open|done`.

Основные маршруты:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/health` | Готовность приложения и доступность моделей без их скачивания |
| `GET /api/meetings` | Список встреч |
| `POST /api/meetings/audio` | Multipart-файл и контекст, быстрый возврат ID |
| `POST /api/meetings/text` | Текст для реальной локальной LLM |
| `POST /api/meetings/demo` | Явно помеченная подготовленная fixture |
| `GET /api/meetings/{id}` | Стадия обработки и результат |
| `PATCH /api/meetings/{id}` | Исправления с проверкой revision |
| `POST /api/meetings/{id}/approve` | Утверждение проверенной версии |
| `GET /api/meetings/{id}/export.docx` | Документ из утверждённой версии |
| `GET /api/meetings/{id}/audio` | Прослушивание исходного файла |
| `GET /api/actions`, `PATCH /api/actions/{id}` | Реестр и завершение поручений |
| `GET /api/notifications` | Напоминания из подтверждённых сроков |

Участник 1 предоставляет `probe`, `process_audio`, `process_text` в `ml.py`. Передай контекст встречи и callback этапа, прими `segments/summary/actions/warnings`. UI не должен знать библиотеку ASR или адрес Ollama.

## План по времени

### 0–15 минут: закрепить стыки

Создать окружение, прочитать существующий код, согласовать payload с участниками 1/3. Определить один способ запуска приложения. Обеспечить лёгкий запуск без тяжёлых ML-зависимостей для работы UI.

Готово: приложение запускается, `/api/health` отвечает, оба участника подтвердили контракт.

### 15–45 минут: хранение и загрузка

SQLite с долговременным сохранением, opaque ID файлов, отдельная папка данных. Загружать файл частями, ограничить размер 100 MB, проверить расширение и фактическую возможность декодирования на ML-этапе. Сохранять дату встречи от пользователя; не заменять её сегодняшней.

Очередь хранится в БД, один обработчик последовательно выполняет тяжёлые задания. На перезапуске явно отмечать прерванные задания, чтобы они не оставались вечными `processing`. Не добавлять Redis/Celery без необходимости.

Готово: встреча переживает перезапуск, UI получает состояние, ошибочный файл даёт понятный ответ.

### 45–75 минут: интеграция

Подключить ML-функции и callback `transcribing/diarizing/extracting`. Успех — `review_ready`, ошибка — `failed` с этапом и понятным сообщением. Пока модели готовятся, demo-route помогает UI работать; он не используется как скрытая замена настоящего inference.

Готово: участник 3 видит реальный результат через backend, а не только fixture.

### 75–120 минут: утверждение и DOCX

Сохранение исправлений с optimistic concurrency: устаревшая revision → 409. Проверять уникальные ID, ссылки на существующие реплики, даты и статусы. Утверждать только готовую встречу, заполненные задачи/исполнителей и вручную разрешённые причины проверки. Отсутствующий срок допустим и отображается явно.

Экспорт из той же утверждённой версии: тема, дата, участники, summary, таблица поручений, источники/транскрипт. Подготовленное демо помечается в документе. Проверить русские и казахские буквы. Правка содержания после утверждения сбрасывает утверждение; отметка исполнения не меняет содержание протокола.

Готово: реальная запись → исправление → утверждение → открывающийся DOCX. Если нет к 120-й минуте — убрать дополнительные интеграции.

### 120–165 минут: контроль исполнения

Реестр использует те же задачи. Выполненные задачи не становятся просроченными. Просрочка и приближение срока рассчитываются по часовому поясу встречи и только по подтверждённой конкретной дате. Событийные сроки автоматически в календарные не превращаются.

Уведомления имеют стабильные ID; повторный запрос страницы не создаёт дубли. Если остаётся время и разрешён внешний канал, можно начать Telegram по разделу ниже.

### 165–240 минут: проверка и сборка

Запустить интеграционные проверки, проверить чистый запуск и сохранение, собрать frontend, передать проверенные команды участнику 3. На 165-й минуте прекратить новые функции, на 210-й — перейти к исправлениям демо.

## Telegram — только после обязательного сценария

Секретарь создаёт участника → выдаётся одноразовый токен → исполнитель сам открывает бота `/start <token>` → сохраняется связь participant_id с user_id и private chat_id. Username не использовать как устойчивый ключ; бот не начинает личный диалог без действия пользователя.

Отправка после утверждения, напоминание перед сроком/при просрочке, кнопка «Выполнено» с проверкой исполнителя. Ключ дедупликации — ID задачи + версия срока + тип сообщения. Сбой Telegram не отменяет утверждение. По умолчанию модуль выключен, token только через окружение. Пока канал не реализован/разрешён, README и UI описывают его как следующий этап.

## Проверки и критерии готовности

- [ ] Настоящий путь загрузки и путь явно помеченного demo существуют раздельно.
- [ ] Данные и версия сохраняются после перезапуска.
- [ ] Параллельная устаревшая правка получает 409.
- [ ] Утверждение с нерешёнными вопросами отклоняется; экспорт неутверждённого документа отклоняется.
- [ ] Источники поручений существуют; неизвестный срок остаётся null.
- [ ] Исправление утверждённого текста требует нового утверждения.
- [ ] Завершённая задача не получает напоминания о просрочке.
- [ ] Ошибка модели отображается как ошибка, не как фиктивный успех.
- [ ] DOCX открывается, включает все задачи и корректные казахские символы.
- [ ] В репозитории нет секретов, записей с чувствительными данными и файлов БД.
- [ ] В README есть проверенный путь установки/запуска, отличия demo и реальных моделей, ограничения доступа.
