# Сквозные проверки с тестовым ML

Заглушка заменяет только блок моделей. FastAPI, загрузка файлов, последовательная
очередь, валидация, SQLite, версии, утверждение, DOCX и React остаются настоящими.
Она нужна для проверки интеграции, **не подтверждает качество ASR, диаризации или LLM**.

## Один запуск

После установки `backend/requirements-dev.txt` в корневую `.venv`:

```powershell
# Из корня, Windows
.\.venv\Scripts\python.exe -m pytest -q
cd frontend
npm ci
npm run test:integration
```

```bash
# Из корня, Linux/macOS
.venv/bin/python -m pytest -q
cd frontend
npm ci
npm run test:integration
```

Node >=22. По умолчанию Playwright использует установленный Google Chrome.
Для установленного Edge задать `PLAYWRIGHT_CHANNEL=msedge`. Для другого Python
задать `E2E_PYTHON` абсолютным путём к интерпретатору с backend-зависимостями.
При отсутствии браузера сначала установить его средствами Playwright и выбрать
соответствующий канал. Запись видео отключена: отдельный FFmpeg Playwright не нужен.

Команда собирает production frontend, запускает изолированный FastAPI на свободном
loopback-порту, выполняет существующие и новые Playwright-тесты и останавливает
созданный сервер. Каждому worker выделяется отдельная папка `artifacts/ml-e2e-*`.
Тесты перезапускают только свой дочерний процесс. Рабочая база `data/` не используется.

Отчёты:

- `frontend/playwright-report/integration/index.html` — HTML;
- `frontend/test-results/integration-results.json` — машиночитаемые результаты;
- `frontend/test-results/integration/` — DOCX, скриншоты, traces при ошибках;
- `artifacts/ml-e2e-*/server.log` — запросы и журнал тестового backend;
- `artifacts/ml-e2e-*/meetings.sqlite3` и `uploads/` — сохранённые тестовые данные.

Все эти результаты исключены из Git. `npm run test:e2e` по-прежнему проверяет
уже запущенный сервер; собственный stub-сервер включается только отдельной
integration-конфигурацией.

## Интерактивная проверка

```powershell
.\.venv\Scripts\python.exe -m backend.testing.server --data-dir artifacts/manual-stub --port 8877 --scenario review
```

После сборки frontend открыть `http://127.0.0.1:8877`. Для аудио-заглушки нужен
корректный непустой PCM WAV. Его декодирование проверяется стандартной библиотекой;
реплики, говорящие и временные метки синтетические. Остальные форматы остаются
ответственностью настоящего ML-адаптера. Текстовый импорт принимает обычный текст.

В UI есть постоянная надпись «Тестовый режим», в summary и неизменяемых warnings —
«ТЕСТОВАЯ ИМИТАЦИЯ ML». Маркировка остаётся в DOCX даже после исправления summary.
Health содержит `details.test_mode=true`, а providers остаются false: реальные
модели не заявляются доступными. Поэтому `backend.smoke` не примет этот сервер
за успешную приёмку настоящего inference.

## Сценарии

Только на тестовом сервере доступен `POST /__test__/scenario`:

```json
{"name":"review","language":"mixed","delay_ms":150,"gate_stage":null}
```

| Сценарий | Результат |
| --- | --- |
| `review` | Три поручения: конкретный срок, событийный срок с неизвестным исполнителем, отсутствующий срок |
| `empty` | Транскрипт и summary без поручений |
| `unavailable` | Явная имитация недоступных моделей; начальное состояние автоматического сервера |
| `fail-transcribing` | Ошибка распознавания |
| `fail-diarizing` | Ошибка диаризации |
| `fail-extracting` | Ошибка извлечения |
| `invalid-evidence` | Несуществующая ссылка на источник; backend обязан отклонить результат |
| `invalid-summary` | Неверный тип summary; backend обязан отклонить результат |

`language`: `ru`, `kz`, `mixed`. Это проверка отображения и сохранения текста,
не лингвистическая оценка. `delay_ms`: 0–10000 на этап. `gate_stage` может остановить
одну стадию; `POST /__test__/release` отпускает её. Ожидание ограничено 60 секундами.
`GET /__test__/state` возвращает журнал стадий и число одновременно активных вызовов.
Настройку нельзя менять во время активного вызова.

Ни один тестовый маршрут не добавляется в production-приложение. Обычные
`python -m backend` и `uvicorn backend.app.main:app` используют исходный ML.
Тестовый launcher требует явный `--data-dir` и отказывается открывать существующую
БД без маркера тестового хранилища. ML-функции подменяются только на время lifespan
отдельного тестового приложения и восстанавливаются после его завершения.

## Покрытие

Новые браузерные проверки выполняют успешную загрузку WAV, все стадии и очередь,
ручное сопоставление голосов, прослушивание источника, Range-запрос, ручное разрешение
вопросов, сохранение/reload, утверждение и скачивание DOCX. Документ действительно
открывается python-docx; проверяются строки задач, даты, исходные формулировки,
казахские символы и неизменность XML утверждённого снимка после завершения задачи.

Дополнительно: RU/KZ/смешанный текст, ошибки каждой стадии, повреждённое аудио и
повторная загрузка, неправильный ответ ML, одинаковые импорты и уникальность ID,
две вкладки с конфликтующими правками, ручное добавление/удаление участника,
поручения и источника, реестр, напоминания, редактирование после утверждения.

Два теста действительно прекращают и заново запускают процесс backend с той же
тестовой базой: один проверяет сохранение файла, версии, статуса и снимка DOCX;
другой — `failed` для прерванного задания и продолжение сохранённого `queued`.

Существующие браузерные тесты дополняют это сетевыми ошибками, настоящим HTTP 409,
клиентским ограничением 100 МБ, согласием на обработку, узким окном и клавиатурой.
Два старых теста специально подменяют ответы GET для проверки отображения; новые
сквозные сценарии не подменяют ответы API в браузере.

Позднее стенд дополнен имитацией Telegram API и браузерными проверками привязки,
уведомлений и завершения поручений: [подробности](TELEGRAM.md). Она не использует
токен из окружения и не отправляет сообщения в сеть. Управление:
`GET /__test__/telegram` — журнал запросов, `POST /__test__/telegram/update` —
тестовый update Telegram, `POST /__test__/telegram/tick` — один цикл доставки.
Бот в этом стенде работает только по явным тестовым циклам, без фонового потока.

Границы: не проверяются реальные веса, качество языков/голосов, GPU, перевод MP3/M4A,
вёрстка DOCX в Word/LibreOffice, живая отправка Telegram/PDF и браузеры кроме выбранного канала.
Отдельный pytest-тест FFmpeg пропускается, если системный `ffmpeg` не установлен.
