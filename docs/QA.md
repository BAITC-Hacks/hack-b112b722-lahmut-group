Дата: 23 сентября 2026 года. Ветка: `codex/frontend-demo`. Изменения ограничены `frontend/`, `README.md`, `docs/demo.md`, `docs/QA.md`. Backend, ML, fixtures и HTTP-контракт не изменялись.

## Окружение и воспроизведение

macOS ARM64; Python 3.12.14; Node 24.19.0; npm 10.9.4; Vite 6.4.3; Playwright 1.63.0. Версии backend — в README. Тестовый backend запущен с `DATA_DIR=/tmp/hatama-ui-qa`, отдельной базой без пользовательских данных. Проверка браузера выполнена Playwright в настоящем Google Chrome 153.0.8010.53. Встроенный инструмент управления браузером Codex не стартовал из-за ошибки sandbox; это не было заменено проверкой только HTTP.

```bash
# Из корня, отдельный терминал
DATA_DIR=/tmp/hatama-ui-qa .venv/bin/uvicorn backend.app.main:app --host 127.0.0.1 --port 8000

# Другой терминал
cd frontend
npm ci
npm run build
npm run dev

# Третий терминал
cd frontend
npx playwright install ffmpeg
PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
# Для production-сборки, которую раздаёт FastAPI:
UI_BASE_URL=http://127.0.0.1:8000 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
```

В этой сессии системных Node/npm и готовой `.venv` не было. Использованы Node из bundled runtime Codex, npm 10.9.4 во временном каталоге и Python venv `/tmp/hatama-ui-venv`. Установка зависимостей, запуск backend по модулю из README, `npm ci` и сборка выполнены фактически. Команда `python3.12` в README предполагает установленный Python 3.12 на машине читателя.

## DOCX

Файл получен кнопкой браузера из утверждённой встречи. ZIP/OOXML корректен; метка demo, изменённый исполнитель и все символы **Ә Ғ Қ Ң Ө Ұ Ү Һ І** сохранены. Файл открыт bundled LibreOffice через `render_docx.py`, отрендерены и визуально проверены обе страницы. Текст читаем, наложений и пропавших букв не обнаружено. Таблица тесная, с одинаковой шириной пяти столбцов — возможное улучшение backend, не изменение frontend.

**Содержательный дефект:** при установленной в интерфейсе дате `2020-01-01` и сохранённом `due_text="К 25 сентября 2026 года"` документ содержит только старую формулировку; `2020-01-01` отсутствует. UI предупреждает об ограничении перед экспортом. DOCX нельзя считать полностью проверенным представлением исправленных календарных дат до изменения backend.

Локальные артефакты (исключены из Git):

- `frontend/artifacts/docx-render/` — две страницы PNG и PDF для визуальной проверки;
- `frontend/artifacts/approved-desktop.png`, `mobile.png` — скриншоты;

## Передача участнику 2

Контракт `contracts/README.md` не менялся. PATCH встречи передаёт `{revision, summary, participants, actions}`, approve — `{revision}`. Пустая дата остаётся `null`, исходный срок сохраняется независимо. Все маршруты идут через `/api`; Vite proxy — `127.0.0.1:8000`.

Задача/канал участника 2 не были доступны, запрос на их указание отправлен пользователю. **Живое согласование не выполнено.** Команда запуска из его задания проверена локально. Этот раздел — подготовленная передача, не утверждение, что участник её принял.

**Приоритетное исправление в зоне backend:** в `backend/app/export.py`, таблица поручений, значение срока берётся как `due_text or due_date`. Нужно выводить исходную формулировку и подтверждённую календарную дату раздельно, если они есть. Не менять `due_text` при изменении календаря во frontend.

Воспроизведение:

1. POST demo, запомнить revision и actions.
2. PATCH с текущей revision: для первой задачи `due_date="2020-01-01"`; `due_text` оставить исходным; у третьей снять `review_reasons` после ручной проверки.
3. POST approve с возвращённой revision.
4. GET export.docx. В документе нет `2020-01-01`, хотя GET встречи и `/actions` возвращают эту дату.
5. Критерий исправления: DOCX содержит и подтверждённую дату, и исходный текст, включая отсутствие даты для событийного срока. Повторить браузерный сценарий и визуальную проверку документа.

Дополнительно: для многопользовательской эксплуатации нужно согласовать версионирование статуса исполнения. Сейчас `PATCH /actions/{id}` меняет status без увеличения revision встречи; параллельное сохранение полного старого массива actions из другой вкладки потенциально может вернуть старый status. Frontend блокирует изменение исполнения при своём несохранённом черновике и обновляет данные после завершения, но серверную межклиентскую гонку это полностью не решает. Этот риск выявлен чтением кода, отдельный конкурентный тест backend не выполнялся.
