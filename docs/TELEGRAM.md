# Telegram: подключение и проверка

Бот реализован как отключаемый канал уведомлений. Он не обрабатывает записи и не
заменяет локальный реестр. В обычном офлайн-режиме `TELEGRAM_ENABLED=false`: бот не
обращается к сети, локальные напоминания продолжают работать.

## Запуск

1. Создать бота командой `/newbot` у официального [@BotFather](https://t.me/BotFather).
   Скопировать выданный токен в локальный `.env` в корне репозитория. Не добавлять
   его в Git, скриншоты или сообщения чата.
2. Настроить окружение:

   ```dotenv
   TELEGRAM_ENABLED=true
   TELEGRAM_BOT_TOKEN=<токен из BotFather>
   TELEGRAM_INCLUDE_TASK_TEXT=false
   ```

   При `false` отправляются только тип уведомления и номер поручения. Такой же
   номер виден в реестре приложения. Для разрешённого демо с вымышленными данными
   `TELEGRAM_INCLUDE_TASK_TEXT=true` добавляет текст поручения и срок.
3. Запустить **один** backend обычной командой `python -m backend` и собранный
   frontend. Дополнительные библиотеки, отдельный процесс бота и публичный сервер
   не нужны: используется [getUpdates](https://core.telegram.org/bots/api#getupdates).
   Username определяется через `getMe`, вручную задавать его не нужно.
   На Windows можно дважды открыть `start-backend.cmd` из корня проекта:
   приложение будет доступно на `http://127.0.0.1:8000`. Окно запуска нужно оставить открытым.
4. В карточке встречи сохранить участников. Исполнитель поручения должен совпадать
   по имени ровно с одним участником. В разделе Telegram нажать «Получить ссылку»
   возле нужного человека и передать её лично ему.
5. Исполнитель сам открывает ссылку и нажимает «Старт». Это одноразовая
   [deep link](https://core.telegram.org/bots/features#deep-linking), срок — 15 минут.
   В приложении появится «Telegram подключён».
6. Проверить поручения и утвердить протокол. Бот отправит назначение; при конкретном
   сроке — напоминание за три дня/при просрочке. Обновления проверяются примерно
   раз в 6 секунд, одному чату отправляется максимум одно поручение за цикл.
7. Нажать «Выполнено». Реестр обновится автоматически. Утверждённый DOCX останется
   снимком исходного протокола; версия встречи увеличится при изменении статуса.

Привязка действует для участника конкретной встречи. Новая встреча требует своей
ссылки. Имя пользователя Telegram не используется для проверки личности.
Участник может остановить уведомления через `/stop`; секретарь — через
«Отключить». Для повторного подключения нужна новая ссылка.

## Ошибки и сохранение

- Telegram выключен или токен не задан: приложение и DOCX работают, ссылка
  подключения недоступна. После настройки окружения перезапустить backend.
- 401: проверить токен. 409: остановить другой процесс этого бота или удалить ранее
  настроенный webhook. Приложение не меняет webhook автоматически.
- 429/сеть: очередь сохраняется, повторная попытка с задержкой; учитывается
  `retry_after`. Утверждение не откатывается.
- 403: пользователь заблокировал бота либо чат недоступен. Привязка отмечается
  отключённой. Разблокировать бота, выдать новую ссылку и снова нажать «Старт».
- 400: сообщение отмечается ошибкой доставки. Статус виден в карточке Telegram.
  Проверить настройки; для повторной доставки после исправления переподключить
  участника новой ссылкой.

База `DATA_DIR/meetings.sqlite3` хранит привязки, хеши приглашений, версии доставки,
очередь, результат отправок и offset Telegram. Повторные циклы/перезапуски не
дублируют подтверждённые отправки. Telegram не предоставляет idempotency key для
`sendMessage`: при сетевом обрыве после приёма сообщения Telegram, но до сохранения
подтверждения локально, повторная попытка может дать дубль. Уже начатую отправку
нельзя отозвать одновременной правкой или отключением. Старые кнопки проверяются
повторно и не завершают изменённые поручения.

Основной сервер остаётся на loopback/SSH-туннеле, как в базовом MVP. Telegram —
внешний канал; включение текстов поручений должно соответствовать разрешённым
данным. Аудио, транскрипт и DOCX бот не отправляет. Токен не включается в логи,
ответы API или исключения адаптера.

## Воспроизводимые проверки без Telegram

Итог прогона 23 сентября 2026: **87 backend-тестов прошли, 1 пропущен**
(отсутствует системный FFmpeg), дополнительно прошли 5 subtests. В это число входят
30 проверок Telegram. **31/31 Playwright-сценарий прошёл** в установленном Chrome,
включая 3 новых сценария Telegram; production-сборка Vite успешна. Скриншоты
панели проверены на desktop и экране шириной 390 px. HTML-отчёт:
`frontend/playwright-report/integration/index.html`, JSON:
`frontend/test-results/integration-results.json`.

Из корня на Windows:

```powershell
.venv\Scripts\python.exe -m pytest -q
cd frontend
npm.cmd run test:integration
```

На macOS/Linux: `.venv/bin/python -m pytest -q`, затем в `frontend`
`npm run test:integration`. Используется установленный Chrome, как в
[инструкции тестового стенда](TESTING_WITH_ML_STUBS.md).

`backend/tests/test_telegram.py` использует настоящий API приложения и SQLite,
подменяя только транспорт Bot API. Проверяются одноразовость и гонки токенов,
истечение, private chat, большие числовые ID, проверки чужих/устаревших кнопок,
неоднозначные имена, повторное открытие задачи, перезапуск, смена аккаунта бота,
дедупликация, границы дат, `/stop`, ошибки сети/429/403/400 и сохранность DOCX.

`frontend/integration/telegram.spec.ts` через Playwright проверяет выдачу ссылки,
имитированный `/start`, утверждение, кнопку завершения, обновление реестра,
неизменность XML DOCX, мобильный интерфейс, перевыдачу/отзыв ссылки и настоящий
перезапуск тестового backend. Тестовый сервер всегда использует фиктивный токен
и транспорт без сети, даже если в `.env` настроен настоящий бот.

Живая отправка Telegram требует отдельной проверки после настройки BotFather и
добровольного подключения тестового исполнителя. Автотесты не доказывают связь с
реальным Telegram. Аддитивные HTTP-маршруты описаны в
[contracts/TELEGRAM.md](../contracts/TELEGRAM.md).
